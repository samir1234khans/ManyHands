# The ManyHands Constitution

**Status:** Foundational and normative

**Applies to:** the official ManyHands product, repository, community, and governance

This constitution defines the promises that should survive changing frameworks, maintainers, designs, and funding models. Product decisions that conflict with it require an explicit constitutional amendment—not a quiet shortcut.

## 1. Problem first

ManyHands begins with a need experienced by people, not with a repository looking for attention. A problem must be understandable without reading code and must be open to more than one proposed solution.

## 2. Coordination here; code on GitHub

ManyHands owns problem discovery, team formation, contribution needs, milestones, progress interpretation, project health, and stewardship. GitHub owns repositories, issues, commits, pull requests, releases, and code review.

ManyHands may summarize GitHub evidence but must not fabricate or obscure it.

## 3. Open by default

The official ManyHands implementation is free software. Forking, experimentation, independent hosting, and upstream contribution are normal parts of the ecosystem.

The official instance earns trust through responsible stewardship. It does not manufacture exclusivity around code that the community built.

## 4. Useful before signup

People must be able to browse public problems, projects, progress, and contribution needs without creating an account. Authentication is requested only when an action needs identity, persistence, permissions, or abuse protection.

## 5. Contributors are co-builders

A contributor is not disposable labor. The product should provide context, ownership, feedback, attribution, and a path to greater responsibility. Early adopters who help build ManyHands should be visibly recognized as founding contributors.

## 6. Progress means evidence

A project may show a percentage only when it is derived from defined milestones. Merged work, releases, demos, verified research, tests, and completed milestones are evidence. Optimistic status text is not.

Projects must show when information is stale, blocked, paused, or seeking a steward.

## 7. No graveyard theater

ManyHands must not make inactive projects look alive. Health is a first-class state. Projects can pause, request stewardship, archive honestly, or resume with a visible history.

## 8. No forced single solution

A problem can support multiple projects. ManyHands must not crown one implementation merely because it arrived first. Discovery can rank quality and health without erasing alternatives.

## 9. Accessible participation

Core workflows must work with keyboard navigation, assistive technology, reduced motion, readable contrast, clear language, and constrained devices. Accessibility is acceptance criteria, not a cleanup phase.

## 10. Privacy and security by design

Collect the minimum data needed. Never expose a private email by default. Tokens and repository permissions must be least-privilege. Authorization is enforced server-side. Security and moderation actions must be auditable.

## 11. Community safety over growth

Harassment, spam, manipulation, malicious projects, and unsafe contribution practices are product risks. Growth does not justify weakening moderation, consent, or user control.

## 12. Human accountability for AI-assisted work

AI tools may accelerate research, design, code, testing, and documentation. They do not become the accountable contributor. A human must understand, verify, test, license-check, and disclose material AI-generated work.

## 13. Boring foundations, ambitious outcomes

Prefer understandable standards, replaceable components, explicit data models, and ordinary deployment paths. Complexity must solve a demonstrated problem. The product can be ambitious without making every layer novel.

## 14. Self-hostable and exportable

The official service may use managed infrastructure, but the application, schema, migrations, and operational documentation must remain sufficient for a competent community to run an independent instance. Public project data should be exportable in documented formats.

## 15. Transparent governance

Authority follows sustained responsibility. Major decisions, conflicts of interest, architecture changes, and governance amendments are documented. Money cannot silently purchase control.

## 16. ManyHands builds ManyHands

The first canonical project on the platform will be **Build ManyHands**. A stranger should eventually be able to discover that project, find a well-scoped need, contribute through GitHub, and have work merged without private handholding. That is the self-hosting milestone.

## Amendment process

A constitutional amendment must:

1. identify the conflict or missing promise;
2. explain the impact on users and contributors;
3. compare reasonable alternatives;
4. remain open for meaningful public review;
5. be approved through the governance process;
6. update related product, architecture, and governance documents in the same change.

Emergency security action may temporarily depart from a process rule, but not from human safety or legal obligations. The departure must be documented when disclosure becomes safe.
