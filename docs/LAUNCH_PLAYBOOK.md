# Founding Community Launch Playbook

The repository should become public while it is alive—not after Samir builds everything and not while it is only a slogan.

## Launch condition

Publicly invite contributors when:

- the foundation pull request is merged;
- the roadmap issue and implementation issues exist;
- at least two issues are genuinely newcomer-safe;
- the first application issue has an active branch and visible progress;
- contribution, conduct, licensing, and security paths are clear;
- Samir can realistically review and respond.

## Founding message

Use a message like:

> ManyHands is a problem-first place for people to build ambitious open-source software together. GitHub will continue to own the code; ManyHands will make the problem, team, progress, and ways to help understandable. The first project is ManyHands itself. You are not arriving after it is finished—you can help decide what it becomes.

## Founding contributor experience

Early contributors should receive:

- visible attribution in releases and the future product;
- clear ownership of a bounded outcome;
- direct access to public product reasoning;
- respectful, timely review;
- a route to stewardship or maintainership through sustained work;
- no implication that unpaid contribution guarantees status or employment.

A future founding-contributor marker should be based on verified contribution, not signup order alone.

## The dogfooding loop

1. GitHub README links to the **Build ManyHands** project in the live product.
2. The project page shows real milestones, open contribution needs, and GitHub evidence.
3. “I can help” routes to the matching issue and contribution guide.
4. A merged contribution updates milestone evidence.
5. The contributor is credited in GitHub and ManyHands.
6. Friction found in this journey becomes prioritized product work.

## Outreach channels

Begin with communities where the problem is relevant, not with indiscriminate promotion:

- open-source maintainers who struggle with contributor onboarding;
- Linux and platform communities with missing software needs;
- designers, researchers, documentation writers, testers, and translators—not only developers;
- contributors looking for meaningful projects rather than random starter issues;
- communities already discussing a specific unmet tool.

Every outreach post should point to one understandable project and one or two actionable needs.

## Avoid

- announcing dozens of empty project categories;
- fake progress percentages;
- calling every signup a founder;
- marking hard architecture work as `good first issue`;
- launching a Discord before contribution flow works;
- waiting passively for contributors;
- promising that community labor will finish the product for the maintainer;
- treating forks as betrayal.

## First public proof

The most credible launch story is not “we built a platform for collaboration.” It is:

> A person who did not know the maintainer found ManyHands, understood the project, chose a task, contributed through GitHub, and saw the project move forward.
