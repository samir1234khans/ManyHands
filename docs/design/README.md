# ManyHands product design

Design work in this directory translates the constitution, product contract, domain model, research, and accessibility baseline into implementation-ready information architecture and interaction behavior.

Design documents do not silently change normative product scope. When design reveals a contract conflict, open a product or architecture proposal and record the decision separately.

## Current handoff

- [`PRODUCT_INFORMATION_ARCHITECTURE.md`](PRODUCT_INFORMATION_ARCHITECTURE.md) — routes, navigation, page hierarchy, core journeys, low-fidelity wireframes, state tables, responsive behavior, accessibility, content rules, components, and engineering acceptance notes.

## Working order

1. Clarify the user and outcome.
2. Define information relationships and state.
3. Map the end-to-end journey, including errors and recovery.
4. Produce low-fidelity structure.
5. Specify responsive and accessible behavior.
6. Define the smallest reusable component/token set.
7. Explore visual styling only after the flow is understandable.
8. Test comprehension with someone unfamiliar with the product.

Source files and exports must remain reviewable in the repository. A proprietary design tool may be used as an aid, but it cannot be the only durable record of behavior.
